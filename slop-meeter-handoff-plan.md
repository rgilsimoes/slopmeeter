# Slop Meeter: Agent Handoff Plan

> Put this file in the new repo (as `PLAN.md` or `AGENTS.md`) and give your agent the kickoff prompt below.

## Kickoff prompt

```
You are building "Slop Meeter" from scratch in this empty repo. Read PLAN.md fully
before writing code. Work milestone by milestone (section 9). After each milestone:
run the tests, commit with a clear message, and report what you did, what you
assumed, and what is still open. Do not skip acceptance criteria. Do not invent
features that are not in the plan; put ideas in docs/IDEAS.md instead. If something
in the plan is ambiguous, pick the simplest option, document it in
docs/DECISIONS.md, and continue.
```

## 1. Purpose

Slop Meeter is a local command-line tool that assesses how much **evidence** a software repository (especially a new, hyped AI tool) provides for what it claims. It answers: *does this project deserve my attention?*

Core idea: **score the evidence, not the vibes.** It does not try to detect AI-generated code. Plenty of solid projects use AI assistance and plenty of slop is handwritten. It measures whether the project has receipts: real history, tests that test, claims with reproducible evidence, plausible attention, and healthy maintenance.

The project is deliberately tongue-in-cheek in tone (README, labels) but **rigorous in method**.

## 2. Principles and non-goals

**Principles**
1. **Deterministic.** Same repo state in, same score out. No randomness, no timestamps in scoring (time-relative checks take "now" as an injectable parameter).
2. **No LLM calls, ever.** Not in the tool, not in its dependencies.
3. **Offline by default.** Network access only with the explicit `--online` flag.
4. **Explainable.** Every check returns evidence (file paths, commit hashes, counts) so users can verify it.
5. **Signals, not verdicts.** Wording must say "no reproducible benchmark found", never "this project is fraudulent".
6. **Safe by construction.** The target repo is untrusted input (see section 8).
7. **Dogfooded.** Slop Meeter scores itself in CI and publishes the result.

**Non-goals (v0)**
- Detecting AI-written code or text.
- Executing the target's code, tests, or quickstart.
- Hosting a website or service.
- Judging code style or architecture quality.
- Originality / plagiarism detection (needs a corpus; out of scope).

## 3. Tech stack

- Python 3.11 or newer, **standard library only at runtime** (`subprocess` for git, `urllib` for online mode, `tomllib` for config, `ast` for Python test analysis).
- Dev dependencies only: `pytest`, `ruff`.
- Packaging: `pyproject.toml` with a console script `slopmeter`; installable via `pipx install .`.
- Verify the package name `slopmeter` is free on PyPI. If taken, pick an available name and record it in `docs/DECISIONS.md`.
- License: MIT unless the owner says otherwise.

## 4. CLI specification

```
slopmeter <path-or-url> [options]

  --online              Enable network checks (GitHub API, package registries)
  --token TOKEN         GitHub token (default: env GITHUB_TOKEN). Never log or print it.
  --format text|json|markdown   Output format (default: text)
  --fail-under N        Exit code 1 if the evidence score is below N (for CI)
  --max-commits N       Cap history analysis (default: 5000)
  --config FILE         slopmeter.toml with weight overrides, ignored paths, buzzword list
  --explain CHECK_ID    Print the definition, thresholds and rationale of a check
  --list-checks         List all checks
  --version
```

- A URL argument is cloned into a temporary directory, analysed, then deleted. A path argument is analysed in place (read-only).
- Exit codes: `0` ok, `1` below `--fail-under`, `2` usage or runtime error.

## 5. Architecture

```
src/slopmeter/
  cli.py            argument parsing, orchestration, exit codes
  repo.py           RepoContext: path, file inventory (size/type), git helpers, safe file reading
  gitlog.py         parsed git history (commits, authors, dates, numstat)
  checks/
    base.py         Check protocol + CheckResult dataclass + registry
    history.py      H1..H5
    tests.py        T1..T3
    claims.py       C1..C3
    docs.py         D1..D5
    deps.py         S1..S4 (S2 online)
    online.py       M1..M3
    info.py         I1 (informational only)
  scoring.py        aggregation, confidence, verdict labels
  report.py         text / json / markdown renderers
  config.py         slopmeter.toml loading and defaults
tests/
  fixtures/builders.py   builds synthetic git repos in tmp dirs
  test_*.py
docs/
  METHODOLOGY.md    the public rubric (generated from check metadata where possible)
  DECISIONS.md      agent decision log
  IDEAS.md          parking lot
  SELF_SCORE.md     generated by CI, never hand-edited
calibration/
  labels.example.csv   template: repo_url,label(solid|mixed|slop),notes
  calibrate.py         runs the tool over labeled repos and reports agreement
.github/workflows/ci.yml
```

**CheckResult** fields: `id`, `name`, `category`, `weight`, `status` (`pass` | `warn` | `fail` | `na`), `message` (one line, neutral wording), `evidence` (list of short strings), `requires_online` (bool).

Every check is a pure function of `RepoContext` (plus an optional injected network client for online checks), so it can be unit-tested with synthetic repos.

## 6. Checks catalogue

Thresholds are starting values. Put them in one `defaults` structure so they can be tuned via config and calibration. Weights are 0 to 5 (0 = informational only).

### Category A: History and substance (category weight 25)

| ID | Check | Logic | Pass / Warn / Fail | Weight |
|---|---|---|---|---|
| H1 | Commit depth | Number of commits (capped by `--max-commits`) | 30 or more / 10 to 29 / under 10 | 3 |
| H2 | Largest-commit share | Share of total added lines in the single largest commit, ignoring lockfiles and vendored paths | under 40% / 40 to 70% / over 70% | 3 |
| H3 | Time spread | Distinct active days and total span | 10 or more days and span of 14 days or more / 4 to 9 days / 3 days or fewer | 2 |
| H4 | Commit messages | Share of generic messages (`update`, `fix`, `wip`, `initial commit`, `Update README.md`, under 10 characters) | under 20% / 20 to 50% / over 50% | 1 |
| H5 | Contributors | Distinct non-bot author identities (normalize by email) | 3 or more / 2 / 1 (never below warn; solo projects are legitimate, so treat this as a mild signal) | 1 |

### Category B: Tests and CI (category weight 20)

| ID | Check | Logic | Pass / Warn / Fail | Weight |
|---|---|---|---|---|
| T1 | Tests present | Test files detected by convention (`test_*.py`, `*_test.go`, `*.test.ts`, `tests/`, `__tests__/`, `spec/`); ratio of test LOC to source LOC | ratio 0.15 or more / above 0 / none | 4 |
| T2 | Tests assert | Python: parse with `ast`, count test functions with at least one `assert`, `self.assert*` or `pytest.raises`, and flag trivially true ones (`assert True`, `assert 1`). JS/TS: best-effort regex on `it(`/`test(` blocks containing `expect(`/`assert`, flag `expect(true).toBe(true)`. Other languages: `na` | 90% or more / 60 to 89% / under 60% | 4 |
| T3 | CI runs tests | CI config present (`.github/workflows`, `.gitlab-ci.yml`, etc.) and contains a test command | both / CI exists but no test step / no CI | 2 |

### Category C: Claims vs. receipts (category weight 20)

| ID | Check | Logic | Pass / Warn / Fail | Weight |
|---|---|---|---|---|
| C1 | Claims have receipts | Extract quantitative or superlative claims from README and top-level docs with regex (for example `\d+(\.\d+)?\s?(%|x|×)`, "faster", "improves", "reduces", "state-of-the-art", "SOTA", "production-ready", "outperforms"). A claim has a receipt if, within 10 lines or the same section, there is a link to an existing in-repo path (`bench*`, `eval*`, `results`, `notebooks`, scripts) or a link to a paper or external source. Score = claims with receipts / total claims | 80% or more, or no claims / 40 to 79% / under 40% | 5 |
| C2 | Eval harness present | If claims exist, is there any benchmark/eval directory or script in the repo? | present / partial (only results, no script) / claims but none | 3 |
| C3 | Hype density | Buzzwords per 1,000 README words (default wordlist in `data/buzzwords.txt`, overridable) | under 8 / 8 to 20 / over 20 | 1 |

Important: C1 and C2 must list each claim and its verdict in `evidence` (line number plus the matched text, truncated).

### Category D: Docs, release and composition (category weight 10)

| ID | Check | Logic | Pass / Warn / Fail | Weight |
|---|---|---|---|---|
| D1 | README essentials | Has a description, an install step, and at least one usage example (code block) | all three / two / one or none | 2 |
| D2 | License | Recognizable SPDX-style license file | present / unrecognized text / missing | 2 |
| D3 | Release hygiene | Tags or releases, or `CHANGELOG`, or version bumps in the history | present / partial / none | 1 |
| D4 | Substance vs. fluff | Share of tracked bytes that is code, excluding lockfiles and vendored paths (the rest being markdown, prompts, JSON, config). A project that is mostly prompts and docs is a "thin wrapper" signal | 25% or more / 10 to 25% / under 10% | 2 |
| D5 | Placeholder density | Share of functions with empty bodies (`pass`, `...`, `NotImplementedError`), plus `TODO`/`lorem` density | under 5% / 5 to 15% / over 15% | 1 |

### Category E: Dependencies and security (category weight 10)

| ID | Check | Logic | Pass / Warn / Fail | Weight |
|---|---|---|---|---|
| S1 | Lockfile / pinning | Lockfile present or versions pinned | yes / partial / no | 1 |
| S2 | Dependencies exist (**online**) | Each declared dependency exists on PyPI / npm. A nonexistent name may be a hallucinated or typosquatted package | all exist / some unverifiable / any nonexistent | 3 |
| S3 | Install-time risk | `postinstall`-style scripts, `curl ... \| sh` in README | none / present but documented / present | 2 |
| S4 | Secrets patterns | High-confidence patterns only (cloud keys, private key headers, common token formats). Never print the secret; print file and line | none / n.a. / any found | 3 |

### Category F: Maintenance and attention, **online only** (category weight 15)

| ID | Check | Logic | Pass / Warn / Fail | Weight |
|---|---|---|---|---|
| M1 | Recency | Age of last commit relative to repo age | recent / aging / stale | 1 |
| M2 | Responsiveness | Median time to first response on issues and PR merge ratio (needs at least 5 issues, else `na`) | healthy / mixed / poor | 2 |
| M3 | Star plausibility | Stars per day of age, share of stars gained in the single busiest week, stars vs. forks vs. contributors vs. issues. Optional `--deep-stars` samples stargazers (account age under 30 days, zero repos) with a hard request cap | plausible / unusual / anomalous. Wording must be "star pattern is unusual", never "fake stars" | 3 |

### Informational (weight 0)

| ID | Check | Logic |
|---|---|---|
| I1 | AI-assistance disclosure | Detects the presence of files like `AGENTS.md`, `CLAUDE.md`, `.cursorrules`, or a disclosure statement in the README. **Never affects the score.** Shown neutrally, so the tool never punishes or rewards AI use. |

## 7. Scoring

- Status points: `pass` = 1, `warn` = 0.5, `fail` = 0, `na` = excluded.
- **Category score** = sum(weight × points) / sum(weight) over applicable checks, scaled to 0 to 100.
- **Evidence score** = weighted average of category scores (category weights above), renormalized over categories that have at least one applicable check.
- **Confidence** = applicable check weight / total possible check weight. Offline runs will show lower confidence because category F and S2 are skipped. Display this prominently.
- **Slop level** (flavor metric) = `round((100 - evidence_score) / 10)`, shown as `n/10` (higher means more slop).
- **Maturity gate:** if the repo is under 14 days old or has under 10 commits, prepend the verdict **"Too early to tell"** but still show the score and all checks.
- **Verdict labels** (evidence score):
  - 80 to 100: "Solid. Receipts included."
  - 60 to 79: "Promising. Some receipts."
  - 40 to 59: "Mostly vibes."
  - 0 to 39: "Peak slop."

Sample text output:

```
Slop Meeter v0.1.0 · target: ./some-tool
Evidence score: 34/100 · Slop level: 7/10 · Confidence: 78% (offline)
Verdict: Mostly vibes. (Too early to tell: 11 commits, 3 days old)

History & substance     42   H2 warn  largest commit holds 82% of added lines (a1b2c3d)
Tests & CI              10   T2 fail  6 of 9 test functions contain no assertions
Claims vs. receipts      0   C1 fail  0 of 4 claims link to evidence (README:12 "37% faster")
...
Info: AI-assistance disclosure: AGENTS.md found (not scored)
```

## 8. Safety rules for the agent (target repo is untrusted)

- **Never execute anything from the target**: no scripts, tests, installs, imports or `git` hooks. Static analysis only. Python analysis uses `ast.parse` on file contents, never `import`.
- When cloning: disable hooks and filters (`-c core.hooksPath=/dev/null`), do not recurse submodules, use a temp directory, clean up on exit (including on error).
- Do not follow symlinks outside the repo root. Skip binary files. Enforce per-file size limits (for example 1 MB) and an overall file-count cap. Add timeouts to every subprocess and network call.
- Network only under `--online`. Identify with a clear User-Agent. Respect rate limits and back off on `403`/`429`. Cap request counts and surface a message when capped.
- Never log or print tokens or detected secrets.
- Output language: neutral and evidence-based. Do not use words like "fake", "scam" or "fraud".

## 9. Milestones and acceptance criteria

**M0. Scaffolding**
Repo layout, `pyproject.toml`, `ruff` and `pytest` config, `slopmeter --version` and `--list-checks` work, CI workflow runs lint and tests.
*Accept:* CI green on an empty-but-valid project.

**M1. Repo context and git history**
`RepoContext`, file inventory, `gitlog` parsing (authors, dates, numstat), synthetic repo builders for tests. Implement H1 to H5.
*Accept:* unit tests cover pass/warn/fail for each H check using builder-generated repos.

**M2. Tests, CI and docs checks**
T1 to T3, D1 to D5.
*Accept:* tests cover a repo with assertion-free tests, a repo with real tests, and a repo with no tests.

**M3. Claims vs. receipts**
C1 to C3 with per-claim evidence. Ship the default buzzword list.
*Accept:* fixtures with claims that have and lack receipts produce the expected evidence lines.

**M4. Scoring and reports**
Aggregation, confidence, maturity gate, verdict labels, text/json/markdown renderers, `--fail-under`, `--explain`.
*Accept:* JSON output validates against a documented schema; two runs on the same repo give byte-identical JSON (inject "now").

**M5. Dependencies and security**
S1, S3, S4 (offline). S2 behind `--online` using an injectable HTTP client so tests use a fake.
*Accept:* no real network calls in the test suite.

**M6. Online maintenance and attention**
M1 to M3 using the GitHub REST API (use `Accept: application/vnd.github.star+json` for star timestamps), with pagination caps and graceful degradation without a token.
*Accept:* all tested with recorded/fake responses; clear messages on rate limit.

**M7. Dogfooding**
CI runs `slopmeter . --format markdown` on the repo itself, writes `docs/SELF_SCORE.md`, and enforces `--fail-under` (start low, for example 40, and raise it over time). README shows the latest self-score. On day one, expect the "Too early to tell" label and keep it: honesty is the brand.
*Accept:* CI publishes the self-score on every push to the default branch.

**M8. Calibration harness**
`calibration/calibrate.py` reads `labels.example.csv`-style files, runs the tool over each repo, and prints score by label and a simple separation metric.
*Accept:* runs on an empty or sample file. **Do not invent labels.** The owner curates the real list (aim for 100 to 200 repos across solid, mixed and slop).

**M9. Docs and release**
`README.md` (tongue-in-cheek tone, honest limitations section, usage, sample output), `docs/METHODOLOGY.md` listing every check, threshold and rationale, `CHANGELOG.md`, tag `v0.1.0`.
*Accept:* a fresh clone can `pipx install .` and run the tool on another local repo.

## 10. Testing strategy

- Build synthetic git repos in temporary directories with a fixture builder (`commit(files, message, date, author)`).
- Golden tests: one "slop-like" repo (single giant commit, no tests, README with unsupported claims) must score clearly below one "solid-like" repo (many commits over weeks, assertive tests, claims with linked benchmarks).
- Determinism test: run twice, compare output.
- Safety tests: a fixture repo with a malicious `.git/hooks`, symlink escaping the root, and a huge file must not cause execution, escape or crash.
- No real network in tests.

## 11. Known limitations (state these in the README)

- Heuristics are gameable; hard-to-fake signals (independent usage, reproducibility) are not measurable offline.
- Claim extraction is regex-based, so expect false positives and negatives.
- Test-assertion analysis is strongest for Python, best-effort for JS/TS, and `na` elsewhere.
- Young repos cannot have history; the tool reports "too early to tell" instead of penalizing them.
- A score is a prompt for scrutiny, not a verdict on the authors.
