# Research notes for the LinkedIn article

This note checks the reasoning behind the criteria in `docs/METHODOLOGY.md`. It is not a validation
of Slop Meeter's numerical model. The sources below support the **direction** of the checks; the
weights, pass/warn/fail boundaries, and composite score remain product-design choices until they are
calibrated against a labelled repository set.

| Slop Meeter criterion | Evidence-backed claim | Primary source(s) | What the evidence does **not** establish |
|---|---|---|---|
| H1–H4: incremental history and commit messages | Separate commits for logically separate changes make a change easier to review as a sequence, while a meaningful log message records the problem, rationale, and rejected alternatives for future developers. | [Git: Submitting Patches](https://git-scm.com/docs/SubmittingPatches) | The source supports reviewable increments and explanatory history, not the 30-commit, largest-commit-share, active-day, or generic-message percentage thresholds. Commit volume and elapsed time are proxies, not proof of authentic or good work. |
| T1–T3: tests, assertions, and CI | Assertions verify expected behaviour; running tests in CI before merging helps catch mistakes early and makes the check repeatable rather than merely promised. | [pytest assertion guide](https://docs.pytest.org/en/stable/how-to/assert.html); [OpenSSF Scorecard CI-Tests](https://github.com/ossf/scorecard/blob/main/docs/checks.md#ci-tests) | Test-file presence, assertion counts, and a test/source LOC ratio do not prove useful coverage or correctness. The 15%, 60%, and 90% boundaries are Slop Meeter heuristics. |
| C1–C2: receipts and reproducible benchmark claims | Performance claims are more credible when the measurement and reporting procedure lets others repeat the experiment and verify the conclusion. Reproducibility review expects artifacts that can recreate the central results, allowing reasonable hardware-dependent variation. | [NIST TN 1830: software performance measurement](https://www.nist.gov/publications/ghost-machine-dont-let-it-haunt-your-software-performance-measurements); [ACM SIGMOD Availability & Reproducibility](https://reproducibility.sigmodconf.hosting.acm.org/index.html) | A benchmark script or link is evidence availability, not independent reproduction or sound experimental design. The “within 10 lines,” 80%, and 40% receipt rules are editorial/product heuristics. |
| D1: README essentials | GitHub describes a README as the place to tell visitors what a project does, why it is useful, how to get started, where to get help, and who maintains it. | [GitHub Docs: About READMEs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes) | A README section can be incomplete or wrong; its presence is evidence of usability effort, not implementation quality. |
| D2: explicit license | Without a license, default copyright applies and others generally lack permission to reproduce, distribute, or create derivatives; an explicit license therefore makes reuse terms inspectable. | [GitHub Docs: Licensing a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository) | A recognised license file does not establish that every bundled dependency or asset is compliant. |
| D3: release hygiene | GitHub releases package deployable iterations, notes, and artifacts around a specific tag, providing a chronological delivery trail users can inspect. | [GitHub Docs: About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases) | A tag or release does not prove runtime quality. Young, internal, continuously deployed, or stable projects may legitimately have no formal releases. |
| S1: lockfiles and pinning | npm says a package lock records the exact dependency tree so later installs can reproduce it; pip likewise recommends exact pins (and, for stronger integrity, hashes) for repeatable installs. OpenSSF says pinned dependencies reduce deployment ambiguity and aid reproducibility. | [npm package-lock documentation](https://docs.npmjs.com/files/package-lock.json/); [pip repeatable installs](https://pip.pypa.io/en/stable/topics/repeatable-installs/); [OpenSSF `pinsDependencies` probe](https://github.com/ossf/scorecard/blob/main/docs/probes.md#pinsdependencies) | Pinning improves repeatability but can freeze known vulnerabilities without an update process. A lockfile alone is not supply-chain security, and “all exact pins” is not equally portable across ecosystems. |
| S3: install-time execution | Package installation can invoke lifecycle scripts such as `preinstall`, `install`, and `postinstall`; npm exposes controls to ignore or explicitly allow them. Their presence is therefore executable attack surface worth inspecting. | [npm install documentation](https://docs.npmjs.com/cli/install/) | Install scripts are not evidence of malice: native modules and build steps can need them. The correct interpretation is “inspect this,” not “guilty.” |
| S4: secret patterns | Hard-coded API keys, passwords, and tokens can be exploited by unauthorised users, creating security, compliance, and financial risk; GitHub scans for them and can block pushes. | [GitHub Docs: Secret-security concepts](https://docs.github.com/en/code-security/concepts/secret-security); [GitHub Docs: Secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning) | Pattern matching has false positives and false negatives; no finding does not prove that a repository contains no secrets. Reports should reveal location and pattern type, never the suspected value. |
| M1–M2: maintenance activity and responsiveness | OpenSSF treats recent commits and maintainer participation in issues as evidence of active maintenance because inactive projects may miss patches. It also explicitly warns that quiet, stable software may need little activity and should be judged in context. | [OpenSSF Scorecard Maintained check](https://github.com/ossf/scorecard/blob/main/docs/checks/internal/checks.yaml); [OpenSSF issue-activity probe](https://github.com/ossf/scorecard/blob/main/docs/probes.md#issueactivitybyprojectmember) | Seven-/30-day response times, merge ratios, age-adjusted recency, and the five-issue sample floor are design judgments. Responsiveness is useful context, not a universal health law. |
| M3: star plausibility | GitHub defines a star primarily as a bookmark and an approximate interest signal. Peer-reviewed primary research has also found large-scale suspicious starring patterns, so stars can be useful context but should not stand alone as proof of quality or authenticity. | [GitHub REST Docs: Starring](https://docs.github.com/en/rest/activity/starring); [He et al., ICSE 2026 paper](https://doi.org/10.1145/3744916.3764531); [authors' replication package](https://github.com/hehao98/StarScout) | The research does not validate Slop Meeter's stars/day, concentration, fork, or issue cutoffs, nor does an anomaly prove purchased/fake stars. “Unusual” or “anomalous” is warranted; accusation is not. |
| I1: AI-assistance disclosure is informational only | GitHub's responsible-use guidance says AI-generated code must still be reviewed, tested, and validated because suggestions can be inaccurate or insecure. That supports judging the observable repository output and its verification trail, whatever tool helped produce it. | [GitHub Docs: Responsible use of Copilot inline suggestions](https://docs.github.com/en/copilot/responsible-use/inline-suggestions); [GitHub Docs: Reviewing AI-generated code](https://docs.github.com/en/copilot/tutorials/review-ai-generated-code) | AI neutrality is a normative product principle, not a scientifically validated claim that human- and AI-assisted code have identical quality distributions. Disclosure can be reported without being rewarded or punished. |

## Methodology caveat worth stating in the article

The closest mature precedent, OpenSSF Scorecard, explicitly says that repository checks and aggregate
scores are opinionated heuristics with false positives and false negatives—not a definitive,
one-size-fits-all verdict. That is strong support for Slop Meeter's “evidence, not vibes” framing **and**
for modest wording about its score. See [OpenSSF Scorecard's project non-goals](https://github.com/ossf/scorecard#project-non-goals).

In particular, no source found scientifically validates Slop Meeter's category weights, score labels,
or individual numeric thresholds. Those values are reasonable initial calibration choices, but the
article should describe them as transparent and configurable heuristics, not natural constants handed
down on stone tablets by the maintainers of Git.
